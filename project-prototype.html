Prototype

What was built, how it was verified, and what is honestly not done yet. This page documents the mock pipeline run from issue #2 (“build the smallest version of the analysis”).

What was built

The core analysis pipeline is implemented as a pure-Python package (project/src/) with no runtime dependencies on the large BTS data files. The modules are:

Pipeline modules

  • networks.py — ODDemand, RouteFlow, build_routes_point_to_point, build_routes_hub_spoke
  • invariants.py — check_endpoints, check_nonnegative, check_simple_path, check_hub_intermediates (passenger conservation is checked separately, in the tests and inside the CLI)
  • legs.py — passenger_legs (counts passenger × flight-leg pairs)
  • totals.py — network_totals (additive over segments, relabelling-invariant)
  • distance.py — distance_nm (great-circle) for 806 airports from OurAirports
  • hubs.py — hub assignment: first hub, or nearest hub
  • db1b.py — DB1B Market demand adapter (10% sample × 10)
  • fleet.py, openap_perf.py, network_perf.py — T-100 aircraft mix per route, OpenAP fuel and NOx per flight, network totals
  • pipeline.py — cli pipeline: all of the above, for both structures
  • t2_check.py, fuel_gap.py — comparison with BTS reported fuel; decomposition of a fuel gap
  • bts_fetch.py — reproducible BTS downloads with a hashed manifest
  • fuel.py, emissions.py, totals.py — the older PLACEHOLDER model, used only by the original cli mode (the 3-airport mock below)
  • figures.py — bar_compare (matplotlib, for exploratory use)
  • cli.py — command-line entry point

The 3-airport mock (issue #2)

Hub: ORD. Spokes: BOS and SFO. Demand: 6 directional OD pairs — BOS↔SFO 100 passengers each way, BOS↔ORD 60 each way, SFO↔ORD 40 each way. Total demand: 400 passengers.

Route distances

Leg Distance (nm) Network
BOS → SFO (nonstop) 2344 Point-to-point only
BOS → ORD 751 Hub-and-spoke leg 1
ORD → SFO 1600 Hub-and-spoke leg 2
BOS → ORD, SFO → ORD (own demand) 751, 1600 Both networks fly these direct

Hub route adds 751 + 1600 = 2351 nm vs 2344 nm nonstop for BOS–SFO — an extra 7 nm via ORD. The difference in passenger-legs (counting each passenger × each flight-leg) is the meaningful quantity here, not distance alone.

How verification works

The tests, in three layers

The pipeline had 319 tests when the mock ran; the suite is now 791 (776 pass and 15 skip when the BTS data files are absent, as on CI). They run with uv run pytest from a clean checkout with no external data; the few tests that need the full BTS files skip, with a stated reason, when the files are not present.

  1. Conservation: the passengers assigned to routes equal the origin–destination demand, in total (within ±1 passenger) and for every OD pair (within 1e-9). The 3-airport mock passes both.
  2. Invariants: every route starts and ends at its OD pair, carries no negative passengers, never visits an airport twice, and in hub-and-spoke only ever connects at a hub.
  3. Mutation testing: each module’s code was deliberately broken in at least three ways (for example, dropping the conservation refusal, or making distance depend on the airport code’s length) to confirm a test fails. Several breaks first went undetected and the tests were strengthened until they were caught.

Status classes on this page (pipeline legend)

The pipeline diagram on the Progress page uses three status classes — each with both a color and a distinct shape so the legend works without relying on color alone:

  • DONE (circle): demand, network builder, invariant checks, T-100 fleet, OpenAP fuel/NOx, CLI
  • IN PROGRESS (triangle): point-to-point feasibility cutoff (only the proxy rule so far)
  • NOT STARTED (square): exposure (adjoint), health burden

CI on every push — a real failure it caught

Continuous integration (CI) runs the full test suite on every push. One real CI failure caught a portability bug. The command-line tool wrote the demand file’s path, exactly as typed, into its manifest.json; given an absolute path, that leaked the machine’s checkout location, so the same inputs no longer gave byte-identical outputs on another machine. The test meant to stop this only searched for /Users/ and /home/, so it passed or failed depending on where the repository happened to be checked out — it passed locally and failed on the CI runner, whose checkout is under /home/runner/. The fix records only the file name (its sha256 identifies the content), with a new regression test that builds its own unique absolute path so it no longer depends on the checkout location.

The six-airport region on real data

cli pipeline now runs BOS, DEN, DTW, MSP, ORD and SFO for 2019 Q1: DB1B demand (2,395,440 passengers), the real T-100 aircraft mix, and OpenAP fuel and NOx for both structures. The outputs are byte-identical across two runs. These totals are outputs of a modelled prototype, not findings: the metric this project compares is population-weighted exposure (ADR 0003), and none of it is computed yet.

Why the totals cannot be compared with BTS directly (and what was found)

Modelled point-to-point fuel (138 kt) is 35% below what the T-100 aircraft kilometres would imply from BTS-reported fuel per nautical mile (212 kt). The gap decomposes exactly into four factors (their product equals the total ratio to 1e-9, a tested identity):

FactorValueReading
Passenger coverage (DB1B ×10 / T-100)0.613largest driver
Flights per passenger0.973close to T-100
Nautical miles per flight1.132model flies longer segments than T-100 averages
Fuel per nautical mile0.963includes 7.4% of departures with no OpenAP model
Product0.650= modelled / reference

A control run feeds T-100’s own passenger counts in as demand. It reproduces T-100 aircraft-nm to 0.2% and fuel to 5%, so the fuel model is not the cause. Coverage is lowest on short pairs (0.37–0.43 on DTW–ORD, MSP–ORD, DTW–MSP) and highest on BOS–SFO (0.89–0.94), which fits a story where DB1B origin–destination demand omits connecting passengers who fill short T-100 legs. That story is consistent with the numbers but has not been tested directly. The control shares its aircraft mix and distances with the model, so it cannot catch an error in those.

Hub assignment is a modelling choice that changes the answer

With hubs ORD and DEN, assigning each airport to its nearest hub sends SFO to DEN (838 nm instead of 1,600 nm to ORD) and everything else to ORD. Hub-and-spoke fuel then falls from 170 kt to 146 kt (−14%), with aircraft-nm down from 22.5 M to 20.7 M. That is a property of the assignment rule, not evidence about hub-and-spoke networks. The earlier default (every airport to the first hub) had made a second hub do nothing. The nearest-hub rule has no decision record yet.

A correction the review made

The agent that built cli pipeline told users to pass --scale 10 for DB1B demand, but the demand file is already multiplied by 10, so following that advice would have inflated every number 100-fold. Found by reading the code against the data, fixed, and covered by a regression test.

What worked

  • Network builder produces correct routes for both topologies from the same demand.
  • Passenger conservation holds exactly (within floating-point tolerance).
  • All four structural invariants pass on both P2P and hub-and-spoke routes.
  • Network totals are additive over segments and unchanged when airports are renamed (with their coordinates moved too).
  • The CLI runs end-to-end from a CSV demand file, and cli pipeline runs the six-airport region on real data with reproducible, hashed inputs.
  • OpenAP fuel per nautical mile is within 8–15% below BTS-reported fuel for five narrowbody types, and the BTS table can be re-fetched and matches its recorded hash.
  • The test suite is mutation-tested, and mutation testing found real gaps that passing tests had hidden.

Not yet done

  • Exposure (GEOS-Chem adjoint): applying the pre-computed adjoint sensitivity fields to route-level emissions is not started. This is the step the research question depends on; everything above is plumbing for it.
  • Health burden: concentration-response function (Turner et al. ozone, GEMM PM2.5) computation is not started.
  • Point-to-point feasibility cutoff (ADR 0007): a nonstop is currently assumed only where T-100 shows one; the check that the assigned aircraft can actually fly the stage length is not implemented.
  • Demand coverage: DB1B origin–destination demand covers 61% of T-100 passengers in the region. Whether connecting passengers explain the rest is untested.
  • Airport codes: 17 of ~12,000 T-100 segments (163 of 1.99 M departures) join the wrong airport because OurAirports reuses some IATA codes, and 1% of departures involve airports not in the table. None are inside this six-airport region.
  • Aircraft coverage: 12% of national departures have no OpenAP model (turboprops, business jets, MD-80 series, Boeing 717) and are excluded from fuel, not estimated.
  • Agent loop (issue #2): a subagent that steps in when a run is invalid is not built; the CLI refuses to write on bad input but nothing repairs it.
