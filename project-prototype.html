Prototype

What was built, how it was verified, and what is honestly not done yet. This page documents the mock pipeline run from issue #2 (“build the smallest version of the analysis”).

What was built

The core analysis pipeline is implemented as a pure-Python package (project/src/) with no runtime dependencies on the large BTS data files. The modules are:

Pipeline modules

  • networks.py — ODDemand, RouteFlow, build_routes_point_to_point, build_routes_hub_spoke
  • invariants.py — check_endpoints, check_nonnegative, check_simple_path, check_hub_intermediates (passenger conservation is checked separately, in the tests and inside the CLI)
  • legs.py — passenger_legs (counts passenger × flight-leg pairs)
  • totals.py — network_totals (additive over segments, relabelling-invariant)
  • distance.py — distance_nm (great-circle; BOS, JFK, ORD, SFO, DEN, PHX today)
  • fuel.py — PLACEHOLDER coefficients (~10–18× too high vs OpenAP)
  • emissions.py — PLACEHOLDER coefficients
  • figures.py — bar_compare (matplotlib, for exploratory use)
  • cli.py — command-line entry point

The 3-airport mock (issue #2)

Hub: ORD. Spokes: BOS and SFO. Demand: 6 directional OD pairs — BOS↔SFO 100 passengers each way, BOS↔ORD 60 each way, SFO↔ORD 40 each way. Total demand: 400 passengers.

Route distances

Leg Distance (nm) Network
BOS → SFO (nonstop) 2344 Point-to-point only
BOS → ORD 751 Hub-and-spoke leg 1
ORD → SFO 1600 Hub-and-spoke leg 2
BOS → ORD, SFO → ORD (own demand) 751, 1600 Both networks fly these direct

Hub route adds 751 + 1600 = 2351 nm vs 2344 nm nonstop for BOS–SFO — an extra 7 nm via ORD. The difference in passenger-legs (counting each passenger × each flight-leg) is the meaningful quantity here, not distance alone.

How verification works

The tests, in three layers

The pipeline had 319 tests when this mock ran (the suite has since grown to about 450 with the BTS and OpenAP modules). They run with uv run pytest from a clean checkout with no external data; the few tests that need the full BTS files skip, with a stated reason, when the files are not present.

  1. Conservation: the passengers assigned to routes equal the origin–destination demand, in total (within ±1 passenger) and for every OD pair (within 1e-9). The 3-airport mock passes both.
  2. Invariants: every route starts and ends at its OD pair, carries no negative passengers, never visits an airport twice, and in hub-and-spoke only ever connects at a hub.
  3. Mutation testing: each module’s code was deliberately broken in at least three ways (for example, dropping the conservation refusal, or making distance depend on the airport code’s length) to confirm a test fails. Several breaks first went undetected and the tests were strengthened until they were caught.

Status classes on this page (pipeline legend)

The pipeline diagram on the Progress page uses three status classes — each with both a color and a distinct shape so the legend works without relying on color alone:

  • DONE (circle): network builder, invariant checks, network totals plumbing, CLI
  • IN PROGRESS (triangle): BTS demand adapter, T-100 fleet, OpenAP fuel/NOx
  • NOT STARTED (square): exposure (adjoint), health burden, point-to-point feasibility cutoff

CI on every push — a real failure it caught

Continuous integration (CI) runs the full test suite on every push. One real CI failure caught a portability bug. The command-line tool wrote the demand file’s path, exactly as typed, into its manifest.json; given an absolute path, that leaked the machine’s checkout location, so the same inputs no longer gave byte-identical outputs on another machine. The test meant to stop this only searched for /Users/ and /home/, so it passed or failed depending on where the repository happened to be checked out — it passed locally and failed on the CI runner, whose checkout is under /home/runner/. The fix records only the file name (its sha256 identifies the content), with a new regression test that builds its own unique absolute path so it no longer depends on the checkout location.

What worked

  • Network builder produces correct routes for both topologies from the same demand.
  • Passenger conservation holds exactly (within floating-point tolerance).
  • All four structural invariants pass on both P2P and hub-and-spoke routes.
  • Network totals are additive over segments and unchanged when airports are renamed (with their coordinates moved too).
  • The CLI runs end-to-end from a CSV demand file.
  • The test suite is mutation-tested, and mutation testing found real gaps that passing tests had hidden.

Not yet done

  • BTS DB1B demand adapter: the streaming chunk reader for the 1.6 GB raw CSV (×10 sample correction, study-region filter) is in progress.
  • T-100 fleet assignment: matching each route to an aircraft type from T-100 (AIRCRAFT_CONFIG=1, ICAO code lookup) is in progress.
  • OpenAP fuel/NOx: current coefficients are placeholder values, not results; calibration against OpenAP reference outputs is in progress.
  • Exposure (GEOS-Chem adjoint): applying the pre-computed adjoint sensitivity fields to route-level emissions is not started.
  • Health burden: concentration-response function (Turner et al. ozone, GEMM PM2.5) computation is not started.
  • Point-to-point feasibility cutoff (ADR 0007): a route is only served nonstop if the assigned aircraft is range-feasible for that stage length; otherwise it remains connecting. Not yet implemented.
